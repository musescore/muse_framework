# 00004 MVVM

Date: 2020-05-30    
Tags: structure, layers  
Maintainers: Igor Korsukov   

## Status: Accepted

## Context

We've often seen presentation and business logic mixed in different applications. When the on-click button handler is used to write the implementation of what needs to be done, when the dialog object simultaneously becomes a service that performs something, etc. Presentation logic is mixed with application domain logic.         
Over time, this leads to enormous difficulties, makes the application inflexible, and becomes a blocker for development, because it does not allow the implementation to be reused in other cases, in other representations.  

## Decision

We will use the Model-View-ViewModel (MVVM) pattern.   

### View 

The primary purpose of a view is to visualize content. Views handle geometry, style, color, animation, and more. We don't think about domain logic here.  
       
We use Qml/Quick technology as a view. We have some views on QWidget - these are outdated views and will be replaced with Qml/Quick.   
      
Location in the module structure:
`modulename/qml/AreaName/ModuleName/...qml`   
This arrangement is due to the requirements of Qml
    
### ViewModel 

The main task of the view model is to prepare data for presentation (formatting, data conversion) and presentation logic - sorting, filtering, presentation scenarios. It is an intermediary between the domain model and the view. We don't think about domain logic here.   
         
We primarily use Qt view models. Typically based on QObject, QAbstractListModel, and having the Q_PROPERTY, Q_INVOKABLE methods. Often these classes have the `Model` suffix - but this is precisely the view model. 
    
Location in the module structure:
`modulename/qml/AreaName/ModuleName/...cpp/h`   
This arrangement is due to the requirements of Qt/Qml

### Model 

What is meant here is "domain model". The domain model is the essence of the module, its domain entities and domain (business) logic. Domain logic can be located in domain entities, or in our case it is more often located in separate services that do something. We don't explicitly highlight the repository layer, in our case it's located in the domain layer, but this can be changed later.          
    
It should not "know" about the representation, because entities can be represented in different ways or interact with them without any representation at all (for example, through a console or a server). We also try not to use technologies related to View (for us it's Qt), but to use pure C++ and STD.  

Location in the module structure:
* `modulename/i...cpp/h` - public interfaces   
* `modulename/moduletypes.h` - public types  
* `modulename/internal/*` - private implementation    

This is how most modules are designed, but there are exceptions.   

## Consequences

* When developing each layer, we can focus on the task of that layer and not think about other aspects - this greatly reduces complexity.   
* We can reuse layers, especially the domain layer, by making a different representation for it or using it without a representation.   
* It may seem like layering is complicated, and a simple task might require creating multiple files in different folders. But that's an illusion. In reality, the complexity is greatly reduced, especially as the application evolves, because the number of entities you need to think about simultaneously is reduced.   
* But we must create functionality in layers, create different files in different folders, and use accepted approaches for interaction.
